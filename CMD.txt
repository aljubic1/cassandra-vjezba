Korak 2
CREATE KEYSPACE IF NOT EXISTS vjezba
  WITH replication = {
    'class': 'SimpleStrategy',
    'replication_factor': 1
  };

USE vjezba;


Kreiranje tablice narudžbi (dizajnirane za query po korisniku):
CREATE TABLE narudzbe (
  korisnik_id UUID,
  created_at  TIMESTAMP,
  narudzba_id UUID,
  ukupno      DECIMAL,
  status      TEXT,
  grad        TEXT,
  PRIMARY KEY (korisnik_id, created_at)
) WITH CLUSTERING ORDER BY (created_at DESC);
Objašnjenje: korisnik_id je partition key — sve narudžbe istog korisnika nalaze se na istom čvoru. created_at je clustering column — narudžbe su sortirane po datumu unutar particije, od najnovije. Ovo čini query 'zadnjih N narudžbi korisnika X' izuzetno brzim.
Kreiranje tablice proizvoda:
CREATE TABLE proizvodi (
  id          UUID PRIMARY KEY,
  naziv       TEXT,
  cijena      DECIMAL,
  kategorija  TEXT,
  dostupnost  BOOLEAN
);
Kreiranje tablice recenzija (dizajnirane za query po proizvodu):
CREATE TABLE recenzije (
  proizvod_id UUID,
  korisnik_id UUID,
  ocjena      INT,
  komentar    TEXT,
  created_at  TIMESTAMP,
  PRIMARY KEY (proizvod_id, korisnik_id)
);
Za provjeru kreiranih tablica:

Korak4
Sve narudžbe određenog korisnika (efikasan query — partition key u WHERE):
SELECT korisnik_id, created_at, ukupno, status
FROM narudzbe
WHERE korisnik_id = 11111111-1111-1111-1111-111111111111;
Narudžbe korisnika od određenog datuma (clustering column range query):
SELECT * FROM narudzbe
WHERE korisnik_id = 11111111-1111-1111-1111-111111111111
  AND created_at >= '2024-01-01 00:00:00+0000';
Paginacija — dohvat prvih N narudžbi:
SELECT * FROM narudzbe
WHERE korisnik_id = 11111111-1111-1111-1111-111111111111
LIMIT 2;
Svi proizvodi u bazi (bez WHERE — prihvatljivo za male skupove):
SELECT naziv, cijena, kategorija, dostupnost
FROM proizvodi;
ALLOW FILTERING — za razvoj i debug (ne koristiti u produkciji):
-- Filtriranje po non-partition key stupcu zahtijeva ALLOW FILTERING
SELECT naziv, cijena FROM proizvodi
WHERE kategorija = 'elektronika'
ALLOW FILTERING;

-- Ekvivalentno za dostupne proizvode
SELECT naziv, cijena FROM proizvodi
WHERE dostupnost = true
ALLOW FILTERING;
Upozorenje: ALLOW FILTERING radi full table scan — kontaktira sve čvorove i skenira sve particije. U produkciji s velikom tablicom može zagušiti klaster. Efikasno rješenje je Secondary Index ili Materialized View (vidi Korak 6).
Provjera TTL-a (time-to-live) na zapisu:
-- Umetni zapis koji automatski nestaje za 60 sekundi
INSERT INTO narudzbe (korisnik_id, created_at, narudzba_id, ukupno, status, grad)
VALUES (33333333-3333-3333-3333-333333333333,
        toTimestamp(now()), uuid(), 9.99, 'test', 'Mostar')
USING TTL 60;

-- Provjeri preostali TTL
SELECT TTL(status), TTL(ukupno), status, grad
FROM narudzbe
WHERE korisnik_id = 33333333-3333-3333-3333-333333333333;

-- Nakon 60 sekundi zapis nestaje automatski



□	pronaći sve narudžbe trećeg korisnika kojeg ste sami dodali u Zadatku 3, sortirane od najstarije (promijenite CLUSTERING ORDER)

SELECT korisnik_id, created_at, narudzba_id, ukupno, status, grad FROM narudzbe WHERE korisnik_id = 33333333-3333-3333-3333-333333333333 ORDER BY created_at ASC;
Zašto smo dodali ORDER BY created_at ASC?
Prilikom kreiranja tablice narudzbe u Zadatku 2, definirali smo zadani redoslijed razvrstavanja (CLUSTERING ORDER BY) kao created_at DESC, što znači da baza podatke automatski vraća od najnovijih prema najstarijima.

Budući da profesor u ovom podzadatku traži obrnuto – od najstarije narudžbe – eksplicitno mijenjamo taj redoslijed pomoću ključne riječi ASC (uzlazno).

Zadatak 4.2: Filtriranje po statusu 'isporuceno' + ALLOW FILTERING
Sada tražimo sve narudžbe u bazi koje imaju status 'isporuceno'. Budući da status nije dio primarnog ključa (baza nije indeksirana po njemu), Cassandra će nam odbiti izvršiti upit osim ako joj izričito ne dopustimo skeniranje pomoću ALLOW FILTERING.

Brisanje samo jednog stupca (ćelije)
U Cassandri možeš obrisati samo jednu specifičnu vrijednost (npr. komentar), a da ostatak retka (ocjena, ID-evi) ostane u bazi. Iskoristit ćemo recenziju koju je Korisnik A ostavio za Laptop (ccd3a17c...).

Provjera:
SELECT * FROM recenzije WHERE proizvod_id = ccd3a17c-a63f-4dff-aa46-7c4dafe278cd AND korisnik_id = 11111111-1111-1111-1111-111111111111;




INSERT IF NOT EXISTS (Uspješan unos)
Ova naredba stvara potpuno novi proizvod s novim generiranim UUID-om, pa će sigurno uspjeti jer taj ID još ne postoji u bazi.
INSERT INTO proizvodi (id, naziv, cijena, kategorija, dostupnost) VALUES (uuid(), 'Novi proizvod', 49.99, 'ostalo', true) IF NOT EXISTS;


UPDATE ... IF status = 'u_obradi'
Sada ćemo testirati uvjetni UPDATE na Korisniku A (11111111...) za njegovu narudžbu iz Zagreba. Iskoristit ćemo onu njegovu prvu narudžbu koja ima timestamp 2026-05-25 06:46:39.799000+0000.
UPDATE narudzbe SET status = 'isporuceno' WHERE korisnik_id = 11111111-1111-1111-1111-111111111111 AND created_at = '2026-05-25 06:46:39.799000+0000' IF status = 'u_obradi';

Budući da je toj narudžbi trenutni status već bio isporuceno (od ranijih upita), ovaj uvjet IF status = 'u_obradi' neće biti ispunjen.
Zato će ti Cassandra u terminalu ispisati [applied] | false i pokazati ti trenutno stanje u bazi.

Ovdje profesor objašnjava kako radi Logged BATCH u Cassandri. Njegova svrha je da spoji više naredbi (u ovom slučaju INSERT i UPDATE) u jedan paket koji se izvršava atomično – ili će proći obje naredbe odjednom, ili neće proći nijedna.

Da bismo ovaj primjer izvrtjeli točno kako piše u skripti, iskoristit ćemo ID našeg Monitora (ccd3a17c-a63f-4dff-aa46-7c4dafe278cd) koji već imamo u bazi.

BEGIN BATCH
 INSERT INTO recenzije (proizvod_id, korisnik_id, ocjena, komentar, created_at) VALUES (ccd3a17c-a63f-4dff-aa46-7c4dafe278cd, 22222222-2222-2222-2222-222222222222, 5, 'Odlicna rezolucija.', toTimestamp(now()));
 UPDATE recenzije SET ocjena = 5 WHERE proizvod_id = ccd3a17c-a63f-4dff-aa46-7c4dafe278cd AND korisnik_id = 22222222-2222-2222-2222-222222222222;
APPLY BATCH;

Materialized View — alternativni pristupni obrazac:
-- MV koji omogućuje pretragu narudžbi po gradu
CREATE MATERIALIZED VIEW narudzbe_po_gradu AS
  SELECT *
  FROM narudzbe
  WHERE grad IS NOT NULL
    AND korisnik_id IS NOT NULL
    AND created_at IS NOT NULL
  PRIMARY KEY (grad, korisnik_id, created_at)
  WITH CLUSTERING ORDER BY (korisnik_id ASC, created_at DESC);

-- Efikasan query po gradu (bez ALLOW FILTERING)
SELECT * FROM narudzbe_po_gradu
WHERE grad = 'Zagreb';
Materialized View automatski održava drugu tablicu s drugačijim primary key-em. Write amplifikacija — svaki INSERT u narudzbe ažurira i narudzbe_po_gradu. Preporučeno za stabilne pristupne obrasce koji se rijetko mijenjaju.

Korak 7 — Constraints i schema validacija
-- Zahtijeva da naziv proizvoda uvijek postoji
ALTER TABLE proizvodi
ADD CONSTRAINT naziv_nn CHECK (naziv IS NOT NULL);

-- U novijim verzijama Cassandre (4.1+), direktno pri CREATE:
-- naziv TEXT NOT NULL,
CHECK constraint na numeričkim vrijednostima:
-- Osigurava da je cijena uvijek pozitivna
ALTER TABLE proizvodi
ADD CONSTRAINT cijena_pozitivna CHECK (cijena > 0);

-- Ocjena mora biti između 1 i 5
ALTER TABLE recenzije
ADD CONSTRAINT ocjena_raspon CHECK (ocjena >= 1 AND ocjena <= 5);
Napomena: CHECK constrainti su dostupni u Apache Cassandri 5.0+. U starijim verzijama validaciju radite na aplikacijskom sloju ili kroz Custom Types.

TRUNCATE i DROP — čišćenje podataka:
-- Briše sve podatke, ali čuva tablicu (brže od DELETE sve particije)
TRUNCATE TABLE recenzije;

-- Briše tablicu kompletno
DROP TABLE IF EXISTS recenzije;

-- Briše cijeli keyspace (ne koristiti u produkciji bez backup-a!)
DROP KEYSPACE IF EXISTS vjezba;
